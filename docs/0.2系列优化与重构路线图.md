## 1. 用户约束与范围

- 从本轮起使用 `0.2.x`。当前默认构建版本为 `0.2.0`；后续阶段版本按实际发布进度递增，不机械地一阶段一版本。
- SVG 暂不维护。保留 `export.svg` 配置项且默认关闭，不要求 SVG 输出兼容或可用，不为它增加测试、重构或性能工作。已有显式开启配置不自动覆盖，测试环境关闭该项。
- 保留单 JAR 部署、Paper/Fabric 双平台、既有线路/站点/编辑配置数据。
- 优先顺序：服务器计算峰值与重复工作 → 正确更新与可诊断性 → 双端业务复用 → 大图交互。
- 不预设引入数据库、WebSocket、Vue/React、全量重写或新的重型依赖。
- 遵守项目 AGENTS 指令：禁止批量删除文件/目录；禁止用清空缓存或清空工作区作为默认排障措施。

## 2. 基线：已经完成、尚未验证

### 2.1 已有实现

项目目录为 `core / paper / fabric`。共享前端位于 `core/src/main/resources/web`，采用 ESM、Canvas 铁路线、SVG 编辑覆盖层和空间索引。这里的 SVG 编辑覆盖层属于网页交互，**不属于暂停维护的 SVG 导出模块**。

0.2.0 已做：

1. Paper/Fabric 的 `reloadRoutesAndRefresh`、`reloadStationsAndRefresh`、`reloadEditsAndRefresh` 不再追加全量重扫。
2. 管理刷新从 `lastBaseResult` 重新应用规则；Paper 与 Fabric 都经 `queueRenderRefresh` 更新待渲染结果。
3. API 增加 `dataRevision`（实例 UUID + 计数）。前端比较已成功加载的 `data.runtime` 与轮询结果；失败不会认可新版本。
4. 新增六个耗时指标：`collectionMs / maxBatchMs / cacheMergeMs / graphMs / rulesMs / renderMs`。
5. 默认构建版本为 0.2.0。双端 SVG 配置默认关闭；Paper 缺项读取默认值也已改为 false。

以上没有引入异步计算，没有完成全量图算法增量化，也没有消除大 Service 或统一双平台 Registry。

### 2.3 已知限制与候选风险

- 局部采集后仍合并缓存并整体建图；采集批次数限制不约束建图/规则/渲染峰值。
- 管理保存减少了扫描，但仍会执行规则处理；route 自动延续存在写 YAML 副作用。
- `webStateJson` 在服务锁内构造完整 JSON；是否是实际热点需测量。
- `dataRevision` 表示网页可读取数据发生变化，不表示 BlueMap marker 已提交或客户端地图已刷新。
- 当前计时是最近观测值，并非同一轮事务的完整追踪；没有 p95、端到端延迟，也不完整覆盖异常路径。
- `drawRails` 遍历全部线路；空间索引目前主要用于查询，不代表绘图已做视口裁剪。
- `nearestLine` 先选最近线再过滤显隐；隐藏线遮挡可见线命中的情况应作为待验证回归场景，不在本文直接宣布已经复现。
- 旧技术文档包含早期设计/默认值。行为冲突时以当前源码、当前配置和可复现结果为准。

## 4. 必须保持的不变量

1. 管理规则始终从原始 base 派生，重复刷新不累计裁切；删除规则能恢复原始可见结果。
2. route 是用户管理身份，component 是物理连通结果。延伸、合并、拆分不得随意改写用户 route 身份。
3. 不在后台线程直接访问平台世界对象；后台输入必须是自有、深度不可变值对象。record 和只读集合外壳不自动证明深度不可变。
4. 显式重扫、世界变化、配置变化有明确失效路径；不能为了减少重扫漏掉已拆除轨道。
5. 前端仅认可成功加载数据自带的版本，不把轮询版本提前视为已加载。
6. 自动延续持久化、marker 提交等副作用必须与有效输入版本关联；旧任务不得覆盖新配置。
7. 双端相同纯数据输入应产生等价业务输出；世界 ID 等平台差异需显式映射。
8. 失败保留最后一次完整可用输出，并明确报告失败；不能把部分失败标为 ready。

## 5. 阶段与依赖

顺序：P0 → P1 → P2 → P3；P4 可在 P0 后作为独立前端批次执行；P5 仅在 P3/P4 测量证明必要时实施。P6 的测试自动化随阶段加入，最后统一收口。不要默认并行派 agent。

### P0：验证并固定 0.2.0 基线（下一位 agent 从这里开始）

**目标**：证明减少重扫没有破坏功能，获得真实负载数据。

操作：

1. 按执行手册保存当前差异清单、构建版本和产物信息；不重置工作区。
2. 在授权测试环境，Paper 后 Fabric 各执行一次管理操作回归矩阵。
3. 同一份可恢复测试数据覆盖：命名/改色/线宽、站点、隐藏、裁切、删除规则、扫描中保存、首次扫描前保存。
4. 对照日志、扫描时间戳、队列与数据版本，确认管理修改不会新建扫描任务。排除同期区块事件的干扰。
5. 记录五类负载：空闲、局部铺轨/拆轨、连续跑图加载区块、管理连续保存、手动全量重扫。
6. 使用同一世界副本及配置做前后对照；记录节点、线段、区块数、MSPT、各阶段耗时与数据/marker 更新时间。
7. 修正阻碍基线回归的具体问题，再开始结构重构。

**验收**：操作矩阵双端通过；结果和证据写入阶段记录。没有真实环境数据时明确记为未验证，不填估计性能提升。

**范围**：测试夹具、必要诊断、最小缺陷修复；不在此阶段搬动全部 Service。

### P1：纯规则共享与可重复后端测试

**前置**：P0 行为已固定。开始修改跨模块边界前做有界 Astra 咨询。

**当前状态**：测试基础已落地，`core: test` 已实际执行 8 个测试并通过；编辑规则计算已迁移到共享 `RailEditProcessor`，两个平台 registry 保留配置读写并委托计算，Paper/Fabric 构建均通过，Fabric 最小启动/API/重扫和有线路 component 隐藏/恢复回归已完成。下一步覆盖 route 匹配、自动延续、跨 chunk、环线以及 component 拆分/合并；不要把当前最小夹具回归误认为完整平台场景。

操作：

1. 给图算法、合并器、route 匹配、隐藏/裁切建立小型固定输入；覆盖坡道、环线、岔点、跨区块、拆分和合并。
2. 在 `core/src/test/java` 建立实际可运行的 Java 测试。当前缺少测试配置，需明确配置测试框架、Gradle test 运行方式，不假定 JUnit 已存在。
3. 逐个提取纯规则。建议先提取编辑规则，再提取 route 匹配，最后统一展示样式/站点数据准备。每次只迁一个职责并双端接回。
4. YAML 读取转成配置 DTO；纯规则返回计算结果及“建议保存的绑定变更”，不在 `apply` 中直接保存 YAML。
5. 平台层保留配置读写、世界访问、命令、事件、生命周期；保存建议必须与当前配置版本校验后应用。
6. API DTO 可共享，但本阶段不必强行合并 HTTP 服务器或配置库。

拟议职责名如 `RouteMatcher / EditProcessor / RenderPlan` 是设计候选，不是已存在的类；以咨询确定的最小边界为准。

**验收**：相同夹具新旧结果等价；相同原始输入重复计算等价；删除规则能恢复；双端不再各自保留被迁出的业务算法；既有 YAML 无需用户手工重建。

### P2：更新协调与读取快照

**目标**：统一更新含义，为异步化准备一致输入输出；先不同时做线程迁移。

操作：

1. 将变化分成展示、业务规则、拓扑、世界采集四类，列清每类需要失效的结果。
2. 明确 `lastBaseResult`、派生结果、待渲染结果、网页数据之间的所有权；每次发布关联世界、规则、配置、生命周期版本。
3. 设计已发布快照供 HTTP 读取，缩短服务锁内工作；完整 JSON 是否缓存由序列化耗时和请求频率决定。
4. 公开数据和管理员数据必须分开构建/缓存，不能泄露隐藏规则或管理字段。
5. 修订号与快照一起发布。无扫描结果时元数据仍可读，不能把它当成几何已生成。
6. 明确队列合并、失败、重试、停用与 reload 语义；补充错误/更新时间诊断。不要用一个模糊 ready 覆盖失败。
7. 审查 HTTP 保存入口实际运行线程；`synchronized` 只提供互斥，不代表已切回平台线程。

**验收**：连续两次管理修改最终为最后一次结果；读取失败下轮重试；公开/管理字段隔离；重载过程中快照可辨识；不丢失待处理世界变化。

### P3：限制主线程峰值

**前置**：P1 纯计算已无文件副作用，P2 发布契约明确；实现前咨询线程/生命周期边界。

操作：

1. 测量确定先优化采集还是建图，不把累计时间误当最长主线程占用。
2. 世界采集留在平台允许线程；在区块数上限外增加时间预算。如果一个区块就超预算，实现区块内部游标，保证暂停/恢复不重复或遗漏节点。
3. 深度不可变快照交给有界后台任务计算建图、规则和展示计划。快照复制本身也必须测量，避免把峰值移到复制阶段。
4. 采用一个运行任务加一个可合并最新请求等有界设计，防止持续铺轨造成无界队列/内存增长。
5. 校验拓扑、规则、配置及生命周期版本。校验在每个实际副作用前执行，不只在后台计算结束时执行。
6. BlueMap API 的线程与生命周期要求先查当前使用版本；只把已确认线程安全的调用移出平台线程。
7. 停用、世界卸载、reload 使旧任务失效；失败保留最后一次完整输出。不得持有服务锁等待后台 Future。

**验收**：可控执行器让旧任务故意晚完成，验证不能修改 marker、文件或 API 输出；双端主线程最大计算片段比基线下降；队列有界，更新最终完成，不因持续变化无限饥饿。

不要预先承诺固定毫秒目标。在 P0 测得服务器余量后，为该测试环境填写明确预算，再以同一硬件和数据验证。

### P4：管理网页大数据与交互

操作：

1. 用现有 `queryBox` 做视口候选筛选，保留线宽与选择容差对应的世界坐标边距。
2. 覆盖跨视口长线、负坐标、多世界、粗线和缩放边界；不能仅以端点在视口内判断可见。
3. 用 `requestAnimationFrame` 合并连续重绘；几何变化重建索引，样式/选择变化尽量复用索引。
4. 验证隐藏线不阻挡可见线命中；必要时让查询阶段接受可见性过滤，而非仅过滤最终一个候选。
5. 保留未保存表单、视口、选择、底图和图层偏好；轮询不能覆盖编辑草稿或让旧请求覆盖新世界状态。
6. 扩展真实浏览器基准：JSON 解析、索引、绘图、平移/缩放帧耗时、内存。已有 10 万线段脚本仅是索引基准。

**验收**：同一数据/视口前后截图和选择语义一致；所有可见线可命中；同规模数据帧耗时改善且没有明显内存退化。

### P5：有证据后再做增量拓扑/marker

**启动条件**：P3 后整体建图或 marker 重建仍是主要瓶颈。有测量证据才启动。

- 先考虑按世界隔离和无变化跳过，再考虑受影响连通分量。
- 新连接可能合并多个分量，删除连接可能拆分整个分量；不能只重建变动区块内的图。
- 稳定 route 身份与 component 重匹配先确定。不要仅用几何接近或采样 hash 决定业务归属。
- marker 差量要求稳定 ID 与删除集合；渲染合并保留来源 component，保证选择/裁切可追溯。
- 测试中对每次增量更新同时用全量算法作为正确性基准，覆盖新增、删除、跨界、循环、合并与拆分。

**验收**：与全量输出在定义的规范化比较下等价；未触及分量不重算；复杂度与内存收益有记录。没有收益或正确性难保证时保留全量纯计算路径。
